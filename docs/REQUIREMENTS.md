## 1. 목적 및 범위
제주빅데이터센터/제주데이터허브의 데이터 1종 이상을 실제 사용하여 비전문가가 자연어로 보행 경로, 생활편의 시설, 지역 인프라를 탐색, 분석할 수 있는 AI Agent를 만든다. 핵심은 **하나의 보행도로 그래프 + 공통 도로구간 지표 + 하나의 통합 CA-MOR 경로 엔진**이다. 별도 안전/와이파이/이동약자 경로 엔진을 중복 개발하지 않는다.

대회 제출 시 기획서(15p 이내), 실행 소스, Prompt, Tool/API 정보, 데이터 출처, 이용조건, 설치/사용 매뉴얼, 검증 결과와 한계가 필요하다. 센터 최소사양: Intel i7-8700, GTX 1060, RAM 32 GB. 제출 마감: 2026-11-20 10:00 KST.

### 기능 범위 및 우선순위
- P0: 자연어 질문과 조건 확인; 최단/안전환경우선/균형 경로; CCTV, 조명, 교통안전 공간지표(실제 확보된 데이터에 한함); 통행 제약; 공중화장실, 약국 경로상 검색; 지도와 근거; 지역 시설 공백 분석; 데이터 출처, 품질 표시.
- P1(데이터 확보 시): 범죄 지역 통계, 시간대별 유동인구, 기상, 도로통제, 이동약자 상세 접근성, Wi-Fi AP 인접성 우선 경로.
- P2: 실측 Wi-Fi 연결 지속성 예측, 전역 검증 무장애 경로, 범죄 예측, 실시간 보행자 밀도.
- 금지: 실제 범죄 피해 확률, CCTV 실제 촬영 범위, Wi-Fi 무중단, 미확인 휠체어 통행가능성을 보장하는 문구.

## 3. 공통 데이터 계약
모든 분석 결과는 동일한 보행도로 edge_id에 연결하고 좌표계, 단위 및 provenance를 고정한다.

```text
RoadEdge:
  edge_id: str
  source_node: str
  target_node: str
  geometry: LineString
  length_m: float > 0
  cctv_index: float[0,1] | null
  lighting_index: float[0,1] | null
  crime_context: float[0,1] | null
  activity_index: float[0,1] | null
  traffic_exposure: float[0,1] | null
  weather_exposure: float[0,1] | null
  accessibility: PASS | BLOCK | UNKNOWN
  closure_status: OPEN | CLOSED | UNKNOWN
  observed_at: datetime | null
  source_ids: list[str]
  resolution: {spatial: str|null, temporal: str|null}
  quality: {coverage: float|null, caveats: list[str]}
```

- NULL은 위험도 0이 아니다. 누락 지표 재정규화와 coverage 별도 출력.
- CCTV/조명 설치 위치는 실제 작동, 촬영 범위, 밝기와 다르다.
- 읍면동 범죄 건수/유동인구를 개별 골목 범죄 확률, 실측 보행량으로 표시하지 않는다.
- 데이터 레지스트리에 원본명, 발행기관, URL, 수집일, 기준일, 라이선스, 원본 해시, 컬럼 매핑, 좌표계, 결측률 기록.
- 제주 공식 데이터 1종 이상 실제 확보/파싱/분석 증빙이 필수 게이트. 미확보 시 가상 데이터 시연은 DEMO로만 표시.

## 4. 통합 경로 알고리즘 CA-MOR
1. 출발, 목적지 위치를 보행 네트워크에 스냅; 스냅거리, 비연결 검증.
2. 각 구간의 통행 제약을 PASS/BLOCK/UNKNOWN으로 판정. 확인된 폐쇄, 불가능 구간 BLOCK은 탐색 대상에서 반드시 제외.
3. 휠체어 등 엄격한 접근성 요청은 PASS로 확인된 구간만 먼저 탐색; 가능 경로가 없으면 검증 경로 부재를 고지. UNKNOWN은 무장애 보증 금지.
4. 가용 데이터로 지표를 산출하고 정규화하되, 타당성 없는 환경 인과 주장은 금지.
5. 경로 유형별 비용을 계산하여 후보 탐색. 예시: `cost(e,u,t) = length_m(e) * (1 + lambda(u) * q(e,u,t))`; q는 관측된 불리한 지표의 가중 결합이며 실제 범죄확률이 아니다. 모든 비용은 비음수.
6. 길이 제한: `length(route) <= (1+detour_ratio) * shortest_feasible_length`. Dijkstra만으로 길이상한을 포함한 최적해 보장 불가: constrained path 탐색 혹은 후보집합+상한 검증, 최적성 주장 시 별도 증명/검증.
7. 최단, 안전환경 우선, 균형 후보의 연결성, 제약 위반, 길이상한, 출처와 누락률 재검증.
8. 공공 와이파이는 AP 설치 위치 인접성만 측정하며 신호 세기/연결 지속성을 보장하지 않는다.
9. 지오코딩 실패, 미연결 그래프, 폐쇄정보 갱신 실패에는 명시적 실패/불확실성 상태를 반환한다.

## 5. 근거 기반 가중치 규정
- 논문 CCTV/조명 개선의 범죄감소 효과크기(예: 13%, 14%)를 직접 `w_cctv`, `w_lighting`으로 대입 금지. 설치 대상 선정의 역인과, 선택편향 고려.
- 우선순위: (a) 제주에서 충분한 공간, 시간, 범죄유형, 노출량 확보 시 공간/시간 분리 검증된 통계효과, (b) 국내외 재현 가능한 연구의 방향, 제약, (c) 설명 가능한 잠정 지표 가중치 + 민감도 실험.
- 범죄 건수는 노출량, 시간창, 공간단위를 고려한다. 가능하면 Poisson / Negative Binomial, 잔차, 공간 자기상관, 오차, 누수 검사. 데이터가 부족하면 위험 추정 회귀를 수행하지 않는다.
- 유동인구는 '사람이 많을수록 무조건 안전'으로 처리하지 않는다. 야간 고립 회피/혼잡 회피 사용자 목적에 따라 방향을 다르게 정의한다.
- 가중치 버전, 출처/DOI, 적용 지역, 데이터 기간, 추정/수동 여부, confidence 및 sensitivity report를 남긴다. 사용자 선호와 실증 위험 관련 변수 분리.
- 추천이 바뀌는 가중치 임계값, 데이터 누락 시 순위 변동, 경로 길이 변화 측정.

## 6. 대화형 Agent
- 의도: ROUTE, POI_NEARBY, POI_ON_ROUTE, AREA_GAP, REPLAN, EXPLAIN.
- 슬롯: origin, destination, departure_time, route_preference(SHORTEST/SAFETY/BALANCED), mobility_profile, constraints, detour_ratio, requested_poi.
- '동문시장 가고 싶어'처럼 경로 유형이 없으면 '안전환경 우선/최단/균형 중 무엇을 원하시나요?'를 질문. 출발지가 미확인일 때 위치 권한 또는 출발지 입력 요청.
- 사용자가 경로 유형을 명시하면 재질문하지 않는다. 후속 '10%만 돌아가'는 해당 슬롯만 수정, 기존 출발, 목적지, 접근성 조건 보존.
- LLM은 도구 선택, 요청 해석, 근거 설명. 도로 탐색/안전지표 수치는 결정론적 Python 모듈이 산출.
- 단일 Orchestrator + tool registry; 무작정 다중 LLM Agent 분할 금지.
- Tool 예시: resolve_place, retrieve_data, get_weather_closures, build_edge_features, find_routes, find_pois, route_via_poi, analyze_gap, validate_result.
- 도구 호출기록, 모델/API 명세, 실패 fallback, 입력 검증, 환각 방지 및 원본값 교차 확인.

- CPU 기반 핵심 경로 계산 작동; GTX 1060/RAM 32GB 센터 PC 기준 설치, 실행 문서.

- 개인정보, GPS 보관 최소화, 위치, API Key, 인증정보를 로그 및 리포지토리에 포함 금지. env.example만 공개.
- 모든 결과에 데이터 기준일, 출처, 관측 가능 범위, 추정/미확인 표시.
- 프론트엔드(모든 Agent 응답 포함)에는 JSON, dict, 구간, 노드 ID, enum 코드(SHORTEST/PASS 등), 내부 필드명 같은 내부값을 노출하지 않는다. 사용자에게는 자연어 문구와 지도, 표 등 시각 요소만 보여준다. 내부 결과는 표시 계층에서 사용자 문구로 변환한다.
- "안전 보장 아님" 같은 공통 안내는 웹 시작 시 한 번만 쉬운 말로 보여주고, 경로 결과마다 반복하지 않는다. "대리변수" 같은 전문 용어는 화면에 쓰지 않는다.
- 예외처리, reproducible fixtures, 테스트 명령, dependency pinning, 라이선스/오픈소스 목록.

## 8. 인수 테스트
- 제주 공식 데이터 원본 ≥1종 사용 및 출처/라이선스/변환 흐름 입증.

- 동일 질의, 고정 데이터, 동일 설정은 동일 결과.
- 미입력 경로 선호 질문/이미 입력된 조건 재질문 방지/대화 중 수정값만 변경.
- POI 직선거리가 아닌 네트워크 우회거리 계산.
- Wi-Fi 무중단 보장 문구 없음.
- 데이터, API 실패 시 오류와 마지막 검증 시점 표시.
- pytest, 정적 검사, 설치 재현, README, 시연 로그, 오픈소스/외부 데이터 명세 완료.

## 9. 단계별 개발 게이트
G0 저장소, 스키마 → G1 공식 데이터 확보 → G2 보행 그래프 → G3 7종 특징 계산기 → G4 가중치 근거/검증 → G5 통행 제약 → G6 CA-MOR → G7 POI, Wi-Fi → G8 지역 공백 → G9 대화 Agent → G10 UI → G11 통합 검증 → G12 제출 패키지.

## 11. 경유지 추천 — 빵집 투어 등 (확정안 r3, 2026-11-16)

자동 일정 생성(v3.0)이 아니라, 출발지, 도착지 사이에 들를 곳을 **같은 규칙**으로 추천하는 기능이다. 두 방식이 있다.
- **단계 선택**(11.1): 한 곳씩 사용자가 고른다. 예: "빵집 투어하고 싶어".
- **자동 추천**(11.2): 사용자가 출발지, 도착지, 여유 시간(또는 들를 곳 수)만 주면 들를 곳과 순서를 한 번에 제안한다. 사용자는 제안된 곳을 하나씩 바꿀 수 있고, 바꾸면 단계 선택으로 이어진다.

**경로 선호**: 도보 구간은 사용자가 고른 최단/균형/안전환경 우선(§4)을 모든 구간에 똑같이 적용하고, 우회 시간도 그 경로 기준으로 계산한다. 차량은 소요시간 최단만 지원한다(차량 안전환경 지표 없음). "현재 위치에서 어디 가고 싶어"(목적지 하나)는 §6의 ROUTE, POI_NEARBY 흐름을 그대로 쓴다.

기존 경유지 추천에서 AI(LLM)는 말을 이해하며, 12절 확장에서는 허용 도구 선택 / 관찰 / 근거 설명도 담당한다. 장소 / 순서 / 시간 계산은 코드가 수행한다. 기존 해석 예시("빵 좋아해" → 빵집 분류, "한 시간쯤 여유 있어" → 여유 60분). 장소 선정, 순서, 시간은 아래 계산 규칙이 정하며, 카카오 장소 검색 결과에 없는 장소를 만들어 내지 않는다(§6 환각 방지). 실시간 위치 추적, 방문 확인은 하지 않는다.

### 11.1 단계 선택 흐름
1. 출발지, 최종 도착지(예: 숙소), 이동수단(도보/차량)을 확인한다. 이미 말한 조건은 다시 묻지 않는다.
   - 출발지: 위치 권한 허용 시 현재 위치, 거부, 실패 시 직접 입력(지명 검색).
   - 도착지가 없으면 묻는다. 사용자가 "다시 여기로 돌아올래"라고 하면 **왕복 모드**: 규칙 (a)를 쓰지 않고 우회 시간 = 출발점→후보 + 후보→출발지 − 0 으로 정렬한다.
   - 지명이 여러 곳이면 후보를 보여주고 고르게 한다.
2. **후보 카드**: 최대 6장(11.5 근거). 카드: 이름, 주소, 계획상 출발점에서의 소요시간, 도착지까지 추가로 걸리는 시간(우회 시간), "카카오맵에서 보기(메뉴, 영업시간은 카카오맵에 등록된 경우만 보임)" 링크. 한 곳만 골라 단정해 추천하지 않는다.
3. 한 곳을 고르면 **계획상 출발점**(첫 단계는 출발지, 이후는 직전에 고른 곳) → 선택한 곳 경로를 보여주고, 그곳이 다음 계획상 출발점이 된다.
4. **다음 후보 규칙**: (a) 그곳→도착지 소요시간 < 계획상 출발점→도착지 소요시간(되돌아가지 않음), (b) 이미 고른 곳 제외, (c) 우회 시간 오름차순, 동률은 이름순. 우회 상한은 두지 않고 카드에 우회 시간을 보여줘 사용자가 판단한다.
5. "그만/숙소로 가자" → 마지막 장소 → 도착지 경로로 마무리하고 전체 동선(지도+순서표)과 총 소요시간을 보여준다. 첫 선택 전에 그만하면 출발지→도착지 경로만 보여준다.
6. 직전 선택 되돌리기를 지원한다. 그 단계부터 다시 계산한다. 임의의 과거 단계 편집은 범위 밖.

### 11.2 자동 추천
1. 입력: 출발지, 도착지, 이동수단, 분류 1개 이상(예: "빵집이랑 카페" → 두 분류를 한 후보 집합으로 합침), 그리고 **여유 시간 또는 들를 곳 수**. 둘 다 없으면 묻는다(임의 기본값 없음). 분류별 개수("빵집 2곳, 카페 1곳")를 말하면 그 개수를 넘는 분류는 다음 단계 후보에서 뺀다.
2. 11.1의 다음 후보 규칙(a)(b)(c)를 매 단계 자동으로 적용해 1순위를 고른다(탐욕적 선택). 다음 1순위를 넣으면 여유 시간을 넘거나 들를 곳 수를 채우면 멈춘다. 각 장소의 체류 시간은 사용자가 말한 값만 쓰고, 없으면 "이동 시간만 계산했고 머무는 시간은 빠져 있음"을 표시한다.
3. 결과: 들를 곳 순서표, 구간별 소요시간, 총 소요시간, 지도. "이동이 가장 덜 늘어나는 순서로 고른 제안이며, 가장 좋은 조합이라고 보장하지는 않음"을 근거 문구로 쓴다(§4.6 최적성 주장 금지).
4. 각 장소 카드에 "다른 곳으로 바꾸기"를 두고, 누르면 그 단계의 후보 카드(11.1-2)를 보여준다.

### 11.3 예외 흐름
- 후보 0곳: "조건에 맞는 곳이 없습니다"와 함께 바로 도착지로 가는 선택지를 준다. **자료 불러오기 실패와 실제 0곳을 구분**해 다른 문구를 쓴다.
- 후보 1곳: 그 1곳과 "바로 도착지로 가기"를 함께 보여준다.
- 일부 후보까지 경로가 없음(그래프 단절): 그 후보만 빼고 "일부 장소는 경로를 계산하지 못했습니다"를 표시한다.
- 자동 추천에서 여유 시간 안에 한 곳도 못 넣음: "여유 시간 안에 들를 곳이 없습니다"와 바로 가는 경로를 보여준다.

### 11.4 계산
- 우회 시간 = (출발점→후보 + 후보→도착지) − (출발점→도착지), 분 단위, 각 항은 **최단 소요시간**. 그래서 항상 0 이상이다.
- **후보 정렬용** 우회 시간은 그래프 탐색 2번(출발점에서 정방향, 도착지에서 역방향 최단 소요시간)으로 모든 후보를 한꺼번에 구한다.
- 사용자가 고른 구간의 **실제 안내 경로**는 그 구간마다 따로 계산하며, 도보는 사용자가 고른 경로 선호(CA-MOR, 우회율 상한 포함)를 적용한다. 화면에 보이는 구간 소요시간은 이 실제 경로 기준이며, 정렬용 우회 시간과 다를 수 있다.
- **여유 시간** = 출발지→도착지 직행(최단 소요시간) 대비 늘어나는 시간(이동 증가분 + 사용자가 말한 체류 시간 합). 자동 추천은 누적 여유 시간이 이를 넘지 않게 한다.
- 출발지가 좌표(현재 위치)이거나 장소 좌표가 도로망 위에 없으면 §4.1 스냅(G2)으로 연결하고, 스냅 실패 시 그 장소는 후보에서 빼고 이유를 표시한다.
- **도보**: 보행 그래프 + CA-MOR(§4). 소요시간은 프로필별 보행 속도(§11.5).
- **차량**: 제주 교통정보센터 도로 링크, 노드(센터 3-07/3-08)로 그래프를 만들고, 링크 소요시간은 요일, 시간대별 평균(센터 3-10)을 쓴다. 소요시간 자료가 없는 링크는 최고제한속도로 추정하고 "제한속도 기준 추정"을 표시한다. 승용차 통행 불가 링크, 미사용 링크는 제외한다. 회전 제한은 방향 정보가 없어 반영하지 못하며 이 한계를 근거에 적는다. 차량 결과는 보행 `edge_id`와 별개이며 §3 보행 지표, §4 CA-MOR 대상이 아니다. 안전환경 표현을 쓰지 않는다. 경로선은 노드를 잇는 선으로 표시하며 "실제 도로 모양과 다를 수 있음"을 근거에 적는다. 평균 소요시간은 실시간이 아님을 표시한다.
- 차량 자료가 없거나 계산에 실패하면 도보로 조용히 바꾸지 않고 실패를 알린다. 경로 유형 질문(최단/안전환경/균형, §6)은 도보일 때만 한다.

### 11.5 수치와 근거
| 값 | 내용 | 근거 |
|---|---|---|
| 카드 최대 6장 | 한 화면 후보 수 | 약한 근거: Iyengar & Lepper (2000)의 6 대 24 선택지 실험. 관광 카드 최적 개수를 입증하지 않음(Chernev et al. 2015: 조건부 효과) → 화면 설계 선택, 시연 후 조정 |
| 일반 보행 1.31 m/s | 도보 소요시간 | 건강한 성인 실외 보통 걸음 메타분석(Murtagh et al. 2021, Sports Med., PMID 33030707) |
| 휠체어 1.04 m/s | 휠체어 소요시간 | 숙련 수동휠체어 사용자 170명 자기선택 속도(PMC4631660). 고정식 에르고미터 실험값이라 실외 적용 미검증 표시 |
| 유모차 | 일반 보행값 사용 | 보행 속도 연구 없음 → 미검증 표시 |
| 우회 상한 없음 | 사용자 판단 | 관광객 우회 허용치를 정한 연구를 찾지 못함 → 숫자를 정하지 않고 우회 시간을 보여줌 |
| 여유 시간, 들를 곳 수 | 자동 추천 중단 조건 | 사용자 입력만 사용(기본값 없음) |

### 11.6 데이터와 이용조건
- **장소 목록 (2026-11-17 변경, 사용자 결정)**: 음식점 공공데이터 파일을 쓰지 않는다. 각 단계에서 "어디 들르고 싶나요?"를 묻고, 사용자가 말한 이름이나 분류("빵집")를 카카오 장소 검색으로 그때그때 찾는다. 이름을 말하면 검색 결과에서 고르게 하고, 분류만 말하면 검색 결과를 후보 카드(11.1-2)로 보여준다. 좌표는 경로, 우회 시간 계산 중에만 쓰고 저장하지 않는다. 플래너에는 카카오 장소 ID와 사용자가 직접 쓴 검색어만 저장하고(가게 이름은 카카오 자료라 저장 안 함), 다시 열 때 다시 검색, 계산한다(카카오 운영정책).
- **카카오맵 링크**: 카카오 장소 ID로 상세 페이지 링크를 연다.
- 향토, 모범, 착한가격 배지는 이번 범위에서 뺀다(음식점 파일을 쓰지 않으므로).
- 메뉴, 가격, 영업시간은 앱이 수집, 생성하지 않는다(센터 메뉴 자료는 반출 불가, 집계 자료).
- 카카오 검색이 실패하면 "장소 검색에 실패했습니다"로 알리고, 검색 결과 0곳(11.3)과 다른 문구를 쓴다. 장소를 공공데이터라고 표시하지 않는다.

### 11.7 인수 테스트
- 후보 7곳 이상 고정 사례에서 카드 정확히 6장, 각 카드에 카카오맵 링크.
- 다음 후보 전부 규칙(a) 충족, 이미 고른 곳 0건, 우회 시간 오름차순.
- 우회 시간 계산이 후보마다 따로 경로 계산한 값과 일치(그래프 탐색 2번 방식 검증).
- 자동 추천: 여유 시간 초과 0건, 들를 곳 수 초과 0건, 매 단계 선택이 그 시점 1순위와 일치. 여유 시간, 수 둘 다 없으면 질문함.
- 자료 실패와 후보 0곳의 문구가 서로 다름.
- 차량 자료 실패 시 도보 대체 결과 0건. 차량 결과에 안전환경 표현 0건.
- 되돌리기 후 그 이전 선택 유지. 폰에서 카카오맵 링크를 열었다 돌아와도 선택 상태 유지.
- 메뉴, 가격, 영업시간을 앱이 생성한 사례 0건. 카카오 검색 결과에 없는 장소 추천 0건. 플래너 저장값에 좌표, 주소 0건.
- 카드, 경로 문구에 내부 ID, 영문 코드, JSON 노출 0건.


## 12. Agent 실행 요구사항: 자연어 안내와 플래너 통합 (2026-11-17 추가)

이 절은 v3.1의 P0 필수 범위다. 1) 목표와 조건 파악, 2) 도구 제공과 선택, 3) 관찰 후 행동 결정, 4) 상태와 메모리, 5) 실패와 복구, 6) 근거와 실행 추적을 구현한다. 평가 요구사항은 13절에 포함한다. 명세 추가는 구현 완료를 뜻하지 않는다.

### 12.0 기존 확정 범위와의 정합성

- 이번 확장은 사용자 요청에 따라 자연어 안내 / 생성 / 수정, 관찰 루프, 상태 관리, 재계획 / 복구, 근거 / 실행 추적을 P0에 추가한다. 기존의 자동 일정 / 재계획 제외는 이 범위에서 해제한다.
- 인물(연예인) 테마 제외, 작은 공공데이터 지식그래프, 카카오 검색 기반 장소 선택, 공급자별 저장 제한, 메뉴 / 가격 / 영업시간을 앱에서 수집 / 생성하지 않는 결정은 유지한다.
- 카카오 유래 장소명 / 주소 / 좌표 / 가공값은 기존 이용조건에 따라 장기 저장하지 않는다. 여행 / 체크포인트에는 허용된 장소 ID와 사용자 입력 등만 보존하고 필요한 정보는 다시 조회한다. 외부 자료를 공공데이터로 바꾸어 표기하지 않는다.
- 자동 일정은 허용된 실시간 조회와 사용자가 제공한 시간 / 체류 조건, 실제 이동비용으로 계산한다. 운영정보를 확인할 수 없으면 미확인으로 표시하며 영업시간 검증 완료를 주장하지 않는다. 아래 도구 계약의 메뉴 / 인물 / 운영정보 관련 필드는 일반 계약의 선택 항목일 뿐, 이번 범위에서 새로운 자료 수집을 허용하는 조항이 아니다.
- 방문 완료 / 진행 상태는 사용자 입력으로 갱신한다. 상시 위치 추적과 자동 방문 감지는 추가하지 않는다.
- 기존 11절의 단계 선택 / 탐욕적 자동 추천은 계속 지원한다. 새 관찰 / 재계획 루프는 이를 호출 / 검증 / 보완하며 데이터 / 권한 / 필수 조건을 임의로 변경하지 않는다.
- 아래 확장과 기존 조항이 충돌하면 Agent의 동작은 12~14절을 적용하고, 데이터 이용 / 보관과 인물 / 메뉴 / 운영정보의 범위는 이 항목과 기존 11.6절을 우선 적용한다.
- 본 문서가 저장소의 최신 요구사항 기준선이다. 루트의 `JEJU_LifePath_AI_SRS_v3.0.md`는 이전 참고 문서이며 그 파일의 넓은 기능 범위를 자동으로 재활성화하지 않는다.

### 12.1 요청 유형과 조건 파악

사용자는 자연어 입력 하나로 이용한다. 필수 모드 선택 화면 없이 현재 요청과 기존 대화를 해석한다. 안내에서 일정 생성으로, 일정 수정에서 단순 조회로 전환해도 맥락을 유지한다.

| 의도 | 예시 | 처리 원칙 |
|---|---|---|
| 안내 / 조회 | 근처 약국 어디야, 이 장소 설명해줘 | 필요한 조회만 수행. 플래너 자동 생성 / 변경 금지 |
| 경로 비교 | 여기서 숙소까지 유모차로 가는 길 | 위치와 이동 조건 해소 후 기존 경로 엔진 호출 |
| 플래너 생성 | 바다와 빵집 들르고 6시까지 돌아오게 짜줘 | 조건 확인, 후보 검색, 실제 이동비용, 시간창, 일정 검증 |
| 플래너 수정 | 여기는 유지하고 점심부터 먹자 | 지시 대상 해소, 명시 변경만 적용, 남은 일정 재계획 |
| 일반 대화 / 미지원 | 인사 또는 제공하지 않는 서비스 | 도구 없는 짧은 답변 또는 지원 범위 안내 |

- AG-101: 자연어 해석 결과는 `intent`, `slots`, `missing_slots`, `ambiguities`, `requested_changes`, `unsupported_features`로 구조화하고 스키마 검증한다. 낮은 확신과 해소되지 않은 지시 대상을 도구 입력으로 확정하지 않는다.
- AG-102: 슬롯은 위치 / 장소 ID, 여행 날짜, 출발 / 복귀시각, 시간대, 이동수단, 이동 프로필, 테마, 체류시간, 고정 / 제외 / 완료 장소, 우회 허용 범위를 포함할 수 있다. 의도에 필요한 슬롯만 필수로 취급한다.
- AG-103: 위치 기반 조회에서 위치가 없으면 위치를 묻는다. 장소 설명에 출발시각을 묻지 않는다. 기존에 확정한 값을 반복 질문하지 않는다. 모호한 지명은 후보를 제시하고 선택받는다.
- AG-104: 한국어 생략, 오타, 이전 응답의 번호 / 장소를 가리키는 표현, 한 메시지의 복수 조건을 처리한다. 단순 조회와 일정 변경이 섞이면 의존 순서에 따라 처리하고 미해결 부분을 구분한다.
- AG-105: 서버 시각과 Asia/Seoul 기준으로 오늘 / 내일 / 오후 6시를 해소한다. 상대시간의 기준시각을 저장한다. 충돌하는 조건이나 여러 해석이 가능한 시각은 질문하며 이전 요청 시각을 현재로 재사용하지 않는다.
- AG-106: 명시값, 이전 확정값, 서비스 기본값, 추정값의 출처를 슬롯별 기록한다. 비핵심 기본값은 표시 후 수정 가능하게 제공한다. 필수 이동제약, 복귀기한, 고정 장소를 임의 추정하거나 완화하지 않는다. 사용자 우회 한도는 설정된 정책 상한 안에서 적용한다.
- AG-107: 정보가 부족하면 `needs_input`으로 반환하고 답변 후 해당 요청을 이어간다. 한 번에 관련된 필수 질문을 묶어 제시하되 불필요한 긴 설문으로 만들지 않는다.

### 12.2 LLM과 도구 계약

단일 오케스트레이터를 기본으로 한다. 다중 에이전트, LangChain / LangGraph 도입 자체는 완료 조건이 아니다. 기존 Python 엔진, FastAPI, SQLite, React UI를 재사용한다. 실행 상태 전이를 코드로 검증할 수 있어야 한다.

LLM은 목표 해석, 검색 전략, 허용된 도구 선택과 인자 제안, 근거 기반 설명을 담당한다. 거리, 시간, 비용, 통행제약, 일정 유효성, 사용자 권한은 서버 코드가 판정한다. 파서는 로컬 제어 단계로 구현할 수 있으며 반드시 LLM 호출 도구로 노출할 필요는 없다.

| 도구 / 단계 | 입력 요약 | 출력 / 실패 계약 |
|---|---|---|
| parse_trip_request | 사용자 입력, 해소된 이전 상태, 기준시각 | 의도, 조건, 누락 / 모호성, 변경 패치 |
| search_places / query_knowledge_graph | 테마, 인물 관계, 지역, 필수 조건 | 후보 ID, 충족 / 미확인 조건, assertion / source ID |
| get_place_details / retrieve_place_evidence | 장소 / 메뉴 / 주장 ID, 방문시각 | 설명, 운영 / 접근 정보, 출처와 유효성 |
| get_valid_constraints | 이동 프로필, 위치 범위, 방문시각 | PASS/BLOCK/UNKNOWN, 적용 조건, 출처 |
| compare_routes / find_routes | 위치 / 출입구, 이동수단 / 프로필, 시각, 우회 한도, 정책 | 경로, 거리 / 시간, 지표, 커버리지, 실패 사유 |
| get_travel_matrix | 후보 출입구, 이동 조건, 출발시각 | 실제 네트워크 이동비용, 도달 불가, 캐시 버전 |
| build_itinerary / plan_itinerary | 후보, 이동비용, 시간창, 체류, 고정 / 제외 | 계산된 일정과 leg, 불가능 조건, 검증할 가정 |
| replan_remaining_trip | 기준 trip_version, 현재 상태, 명시 변경 | 후보 새 버전, 차이, 검증 결과. 즉시 최신 상태 덮어쓰기 금지 |
| find_nearby_facilities / search_pois / rank_detours | 위치 / 경로, 유형, 범위, 우회 한도 | 시설 후보, 직선 근접 / 실제 경유 구분, 운영 미확인 |
| analyze_coverage_gap | 구역, 시설, 기준 | 접근거리, 시설 분포, 자료 커버리지 |
| validate_itinerary / validate_result | 일정 / 경로 / 주장, 확정 제약과 근거 | 오류, 경고, 검증 수준, 게시 가능 여부 |
| get_trip_state / apply_trip_patch | 서버에서 부여한 사용자 범위, 여행 ID, 기대 버전, 변경 패치 | 소유권 검증된 상태, 원자적 변경 또는 버전 충돌 |

슬래시로 병기한 도구명은 같은 책임의 후보 이름이다. 구현은 하나의 정규 이름을 선택하고 기존 함수 대응표를 작성한다. 같은 책임을 중복 도구로 모두 등록하지 않는다.

- AG-201: 도구 레지스트리에 설명, 입력 / 출력 스키마, 지원 능력, 읽기 / 변경 구분, 오류 분류, timeout, 재시도 / idempotency 정책을 선언한다. 인자를 실행 전에 검증한다.
- AG-202: 실제 연결되어 사용 가능한 도구만 LLM에 제공한다. 호출 권한과 사용자 ID는 인증 세션에서 주입하며 LLM이 정한 사용자 ID를 신뢰하지 않는다. 도구 인자로 SQL / 셸 / 임의 URL 실행을 허용하지 않는다.
- AG-203: LLM 제공자는 교체 가능한 어댑터로 구현한다. 기존 키 설정을 조사하고 base URL, model, timeout을 설정으로 제공한다. 특정 제공자의 API 호환성을 확인 없이 가정하지 않는다. 실제 tool calling 응답 또는 구조화 출력을 검증한다.
- AG-204: provider / key가 없으면 계산 엔진과 수동 플래너는 계속 이용 가능해야 한다. 규칙 기반 제한 모드, mock LLM, 실 LLM을 명시적으로 구분한다. mock 성공을 실 LLM 검증으로 보고하지 않는다.
- AG-205: 기존 RouteStatus의 대문자 상태와 Agent 응답 상태는 어댑터에서 명시 매핑한다. 경로 없음, 자료 없음, 미지원, 조건 충돌, 시스템 장애를 한 오류로 합치지 않는다.
- AG-206: Agent API, 수동 UI, 일정 저장에 이동 프로필과 사용자 제약을 일관되게 전달한다. 프론트 기본값으로 서버의 조건을 덮어쓰지 않는다.

### 12.3 관찰과 다음 행동 결정

기본 흐름은 `해석 → 정보 보완 또는 도구 선택 → 실행 → 결과 관찰 → 추가 조회 / 재계획 / 검증 / 응답`이다. 모든 요청에 같은 도구 순서를 강제하지 않는다. 필요한 정보가 이미 있으면 추가 호출 없이 종료할 수 있다.

- AG-301: 도구 결과의 성공 여부, 후보 수, 누락 자료, 조건 충족, 근거 유효성을 관찰하고 다음 행동을 결정한다. 단일 호출 결과를 무조건 최종 답변으로 복사하지 않는다.
- AG-302: 유모차 요청에서 계단이 확인된 후보를 찾으면 제외 후 다른 후보를 조회한다. 후보가 없으면 지역 / 검색어 등 검색 전략을 바꿀 수 있으나 필수 접근 조건이나 복귀기한은 몰래 바꾸지 않는다.
- AG-303: 검색 반경 확대, 대체 테마 탐색은 명시 조건과 충돌하지 않는 범위에서 수행한다. 하드 제약 완화가 필요하면 충돌과 가능한 변경안을 제시하고 사용자의 선택을 기다린다.
- AG-304: 일정 / 경로는 계산 도구와 독립 검증을 거친 후 게시한다. 운영시간 / 접근성 자료가 없으면 검증되지 않은 항목을 표시한다. 필수 제약을 검사하지 못한 후보를 `ok` 확정 일정으로 승격하지 않는다. 결과에 부분 검증 수준을 표시한다.
- AG-305: 도구 호출 수, 모델 호출 수, 실행 총시간, 도구별 시간, 후보 수, 재계획 횟수, 동일 실패 반복을 제한한다. 초기 제한은 `configs/agent_policy.*`에 잠정 운영값으로 명시하고 실측 후 조정한다. 200개 경로 후보 제한을 시간제한으로 간주하지 않는다.
- AG-306: 제한 도달 / 취소 시 새 호출과 상태 게시를 중단한다. 알려진 부분 결과와 미해결 조건을 반환한다. timeout 이후 늦게 도착한 작업이 여행 상태를 변경하지 못하도록 실행 토큰 / 버전으로 차단한다.

### 12.4 상태, 메모리와 동시성

대화 전문만 프롬프트에 넣는 방식으로 상태 관리를 대체하지 않는다. 확정 조건과 변경 이력을 구조화하여 저장한다.

| 상태 | 최소 필드 |
|---|---|
| DialogueState | 소유자, 대화 ID, 의도, 슬롯과 출처, 부족한 항목, 질문, 대상 여행, revision |
| TripState | 여행 ID / 버전, 날짜 / 시간대, 이동 조건, 고정 / 제외 / 완료 / 진행 장소, 현재 위치 참조, 복귀기한, 일정 / 경로, 데이터 / 정책 버전 |
| RunState | run_id, request_id, message_id, 기준 여행 버전, 실행 단계, 예산, 관찰 결과 참조, 오류, 마지막 체크포인트, 취소 상태 |
| ToolInvocation | invocation_id, 정규 도구명, 인자 해시 / 마스킹 입력, 시도 번호, 상태, 시작 / 종료시각, 결과 / 근거 참조, idempotency_key |

- AG-401: 일반 안내만으로 여행 상태를 생성 / 변경하지 않는다. 일정 변경은 사용자가 요청한 패치만 반영하고 나머지 명시 조건을 보존한다. 완료 장소는 남은 일정에서 재방문 대상으로 넣지 않는다. 재방문을 명시 요청하면 별도 방문 항목으로 표현한다.
- AG-402: 고정 / 제외 충돌, 고정 장소의 운영 불가, 복귀기한 초과는 명시적 충돌이다. 고정 항목을 조용히 제거하거나 조회 실패로 삭제하지 않는다.
- AG-403: SQLite 등 기존 저장소에 migration을 추가하고 기존 계정 / 플래너를 보존한다. 요청별 안전한 연결 / 트랜잭션을 사용하고 공유 단일 연결에서 무잠금 동시 변경을 허용하지 않는다.
- AG-404: 후보 일정은 staging 상태로 만들고 검증 후 `expected_trip_version`을 확인하는 원자적 트랜잭션으로 게시한다. 버전 불일치는 충돌로 반환한다. 오래된 실행 결과가 최신 일정을 덮어쓰지 않는다. UI도 응답의 여행 / 요청 버전을 확인한다.
- AG-405: 사용자 메시지 중복 전송과 네트워크 재전송은 message_id / request_id와 idempotency_key로 중복 적용을 막는다. 동일 ID에 다른 payload가 오면 충돌이다. 중복 요청으로 같은 일정 변경을 두 번 실행하지 않는다.
- AG-406: 세션 대화 메모리와 사용자가 저장한 여행 계획을 구분한다. 장기 선호 / 방문 이력은 기본 비활성으로 두고 별도 동의 / 삭제를 지원한다. 로그와 체크포인트의 정밀 위치는 최소화하며 재개에 필요한 경우 소유자 제한, 보유기간, 만료 / 삭제 정책을 둔다. 공급자별 좌표 저장 제한을 준수한다.
- AG-407: 캐시 키는 위치 / 출입구, 이동수단 / 프로필, 관련 제약, 방문시각, 데이터 스냅샷, 정책 버전을 포함한다. 조건 변경 시 이전 캐시를 무조건 재사용하지 않는다.

### 12.5 실패, 재계획과 중단 후 복구

| 분류 | 다음 행동 |
|---|---|
| 일시 장애 / rate limit | Retry-After와 남은 예산을 고려해 제한적 재시도 / backoff |
| 잘못된 인자 | 스키마 오류 반환. 제한적으로 인자 보정 후 재검증 |
| 인증 / 설정 / 미지원 | 무한 재시도 금지. 가능한 제한 기능과 설정 누락 안내 |
| 정상적인 빈 결과 | no_results로 관찰. 조건을 유지한 검색 전략 변경 |
| 필수 조건 충돌 / 경로 없음 | infeasible 이유와 변경안 제시. 조건 자동 해제 금지 |
| 원천 만료 / 누락 | unavailable / unverified 표시. 최신 정보로 단정 금지 |
| 검증 실패 | 게시 차단, 원인에 맞춘 제한적 재계산 |
| 취소 / deadline | 새 작업 중단, 체크포인트 정리, 늦은 변경 차단 |
| 버전 충돌 | 최신 상태 재조회 후 사용자 변경 의도와 재조정. 오래된 결과 게시 금지 |

- AG-501: 도구별 오류 분류와 retryable 여부를 명시한다. 모든 예외를 빈 검색 결과로 처리하지 않는다. timeout과 HTTP 오류 등 알려진 오류를 분류하고 내부 예외 / 키를 사용자에게 노출하지 않는다.
- AG-502: 작업 의도와 invocation을 실행 전에 기록하고, 완료 결과와 다음 실행 단계를 안전한 경계에서 저장한다. 프로세스 재시작 후 미완료 invocation의 불확실한 실행 여부를 판정한다.
- AG-503: 읽기 조회는 최신성 정책 안에서 결과 재사용 / 재호출 가능하다. 내부 여행 변경은 트랜잭션과 idempotency 기록으로 중복을 막는다. 비멱등 외부 변경은 현재 범위에 없으며 추후 도입 시 제공자 멱등성 없이 재실행하지 않는다.
- AG-504: 재개 시 소유권, 만료, 여행 버전, 취소 여부, 원천 최신성을 확인한다. 운영시간 / 기상 / 통제처럼 시간에 민감한 결과는 만료 시 재조회한다. 체크포인트가 오래됐으면 그 사실을 표시하고 최신 조건에서 재계산한다.
- AG-505: LLM 응답 대기나 도구 timeout을 포함해 실제 wall-clock deadline을 적용한다. 취소할 수 없는 작업의 결과도 게시 단계에서 차단한다. 호출 횟수만 줄이고 실행시간 무한 대기를 남기지 않는다.

### 12.6 근거와 실행 추적

- AG-601: 운영시간, 가격, 인물 추천 / 방문, 접근성 등 검증 가능한 사실을 claim 단위로 source / assertion / 원문 위치 / 확인일에 연결한다. URL이 존재한다는 이유만으로 그 주장을 뒷받침한다고 판정하지 않는다.
- AG-602: 거리 / 시간 / 점수 등 계산 주장은 사용한 도구 결과, 입력 해시, 데이터 스냅샷, 정책 버전에 연결한다. 모델 설명 숫자는 검증된 계산값을 사용한다.
- AG-603: trace는 도구 선택의 짧은 결정 사유 코드 / 요약, 검증된 인자, 결과 상태, 시각, 소요시간, 재시도, 오류, 사용량 / 비용(확인 가능할 때)을 기록한다. 모델의 비공개 추론 전문이나 생각 과정을 수집할 필요는 없다.
- AG-604: 사용자에게는 출처 / 확인일, 추천 이유, 가정과 미확인 항목을 제공한다. 상세 trace는 해당 사용자 또는 권한 있는 개발자만 조회한다. 기본 화면에 JSON, 내부 ID, 예외 stack trace를 나열하지 않는다.
- AG-605: API 키, 인증 헤더, 비밀번호, 세션 토큰은 trace에서 제외한다. 정밀 위치, 대화 원문은 필요한 최소한만 보유하고 설정된 만료 / 삭제 정책을 적용한다. 평가에는 합성 사용자 정보를 사용한다.
- AG-606: 외부 검색 결과와 문서의 지시는 데이터로 취급한다. 문서가 도구 권한 / 하드 제약 / 시스템 지시를 바꾸지 못해야 한다. 최종 설명이 검증 결과와 불일치하면 정정 또는 게시 차단한다.

### 12.7 API와 공통 응답

인증된 대화 요청 / 재개 / 취소 / 상태 조회 인터페이스를 제공한다. 경로 예시는 `POST /api/agent/messages`, `POST /api/agent/runs/{run_id}/resume`, `POST /api/agent/runs/{run_id}/cancel`, `GET /api/agent/runs/{run_id}`다. 기존 API 관례에 맞춰 이름을 조정할 수 있으나 소유권 / 버전 계약을 보존한다. 별도 상태 polling 또는 streaming은 구현 선택이며 SSE 자체는 필수 아님.

공통 응답: `request_id`, `run_id`, `conversation_id`, `trip_id`(nullable), `trip_version`(nullable), `status`, `message`, `questions`, `itinerary`, `routes`, `claims`, `evidence`, `missing_data`, `warnings`, `policy_version`, `dataset_snapshots`, `trace_ref`와 사용자용 실행 요약. 전체 원시 trace는 권한 있는 상세 조회로 분리한다.

응답 상태는 `ok / needs_input / partial / infeasible / unsupported / error / cancelled`로 구분한다. 실행 단계는 별도로 `pending / interpreting / awaiting_input / running_tool / observing / validating / committing / completed / failed / cancelled` 등을 사용한다. `partial`에는 사용 가능한 범위와 게시하지 못한 항목을 함께 담는다.

## 13. 오픈소스 평가와 Agent 인수시험

### 13.1 오픈소스 평가 구성

평가 도구는 `AgentEvals + pytest`를 필수 기반으로 하고 `DeepEval`은 대화 품질 보조 평가로 선택한다. 평가 실행은 로컬 명령으로 제공한다. SaaS 가입 / 외부 trace 업로드를 필수로 만들지 않는다. GitHub Actions 자동 실행이나 유료 서비스 설정은 이 증분의 필수가 아니다.

| 구성 | 역할 | 판정 방식 |
|---|---|---|
| AgentEvals | 도구 선택, 인자, 필요한 선후관계, 실행 과정 평가 | trajectory match / 허용 경로 규칙. 필요할 때 LLM judge 보조 |
| pytest | 시간 / 경로 제약, 상태 보존, 버전 충돌, 소유권, 멱등성, deadline, crash recovery | 실제 함수 / 저장소 / API의 결정론적 assertion과 장애 주입 |
| DeepEval (선택) | 목표 달성, 재질문 적절성, 다중 대화 품질, 근거 기반 설명 | 루브릭, 기준 답안 / 증거, 사용 모델 / prompt 버전 고정 |

- EVAL-01: 구현 시 공식 API / 라이선스 / 의존성을 확인하고 동작 검증한 버전을 lockfile 또는 별도 eval 의존성 파일에 고정한다. 이름이 비슷한 비공식 패키지로 대체하지 않는다.
- EVAL-02: AgentEvals 실제 evaluator에 실제 실행 trace를 전달하는 어댑터와 실행 명령이 있어야 한다. 설치 / import / mock 점수 반환만으로 통합 완료 처리하지 않는다. 공식 evaluator와 자체 하드 제약 검증 결과를 구분한다.
- EVAL-03: 모든 요청에 정확히 같은 도구 순서를 정답으로 두지 않는다. 필수 호출, 금지 호출, 선행 조건, 인자 제약과 허용 대체 경로를 사용한다. 근거를 먼저 확보했으면 추가 조회를 강제하지 않는다.
- EVAL-04: 전체 trace의 도구 인자와 응답, 최종 상태 / 상태 변경, 최종 답변을 함께 평가한다. 성공 문구만으로 실제 일정 저장 / 조건 충족을 판정하지 않는다.
- EVAL-05: 평가 케이스마다 ID, 입력 턴, 초기 상태, fixture / API 모드, 기대 의도 / 슬롯, 허용 도구 조건, 필수 결과 / 금지 결과, 주장 근거, 장애 주입, 판정 방식을 정의한다.
- EVAL-06: 개발용 케이스와 보류 평가용 케이스를 구분하고, 실행 후 유리한 결과만 고르지 않는다. 실 LLM 비결정성 확인은 동일 케이스를 사전 설정한 횟수 반복해 실행한다. prompt / 모델 / 데이터 / 정책 / 코드 커밋을 기록한다.
- EVAL-07: 하드 제약 위반, 권한 우회, 상태 손실, 중복 변경, 오래된 결과 게시, 무근거 확정 주장은 테스트셋 내 허용 0건이다. 이는 실제 배포에서 0위험을 증명하는 수치가 아니다.
- EVAL-08: 목표 달성률, 의도 / 슬롯 정확도, 불필요한 질문, 도구 적합성, 상태 보존율, 복구 성공률, 근거 오류, p50/p95, 호출 수와 비용을 분리 보고한다. 일부 항목의 높은 평균으로 하드 실패를 상쇄하지 않는다. 품질 점수의 임계값은 베이스라인 측정 후 잠정값임을 표시해 정한다.
- EVAL-09: mock / synthetic, 제한된 실 API, 실 LLM E2E 평가를 구분한다. 실행 불가 항목은 `NOT_RUN`과 사유로 표시하며 통과 분모에 넣지 않는다. 데이터 부족과 도구 장애를 구분한 집계도 제공한다.
- EVAL-10: LLM judge는 선택이며 API 사용료가 생길 수 있다. 모델 / endpoint / 예산을 설정하고 키 없는 결정론적 평가를 기본으로 제공한다. judge 결과는 표본 사람이 검토할 수 있는 근거 / 루브릭을 포함한다. 한국어 적합성을 확인한다.

공식 참고: https://github.com/langchain-ai/agentevals , https://github.com/confident-ai/deepeval , https://docs.pytest.org/ . 평가 도구는 실행 기반이며 제주 도메인 정답셋을 자동으로 제공하지 않는다.

### 13.2 Agent 추가 인수시험

아래 항목은 기존 8절 / 11.7절 인수시험을 대체하지 않고 추가한다. 각 묶음은 복수의 정상 / 경계 / 실패 케이스로 구성할 수 있다. 표의 개수 자체를 품질 점수로 사용하지 않는다.

| TC | 시나리오 | 필수 결과 |
|---|---|---|
| AT-01 | 위치 없는 근처 약국 조회, 위치 답변 후 재개 | 위치만 재질문, 기존 요청 유지, 확인 안 된 영업 단정 없음 |
| AT-02 | 장소 설명 / 인사 / 경로 / 일정 생성 요청 | 올바른 의도. 단순 안내가 여행을 변경하지 않음 |
| AT-03 | 모호한 장소명 / 이거 빼줘 / 번호 지시 | 후보 / 지시 대상 해소 전 임의 삭제 없음 |
| AT-04 | 오늘 / 내일 / 자정 경계 / 복귀시각 | Asia/Seoul과 기준시각으로 해소. 시간 충돌 처리 |
| AT-05 | 유모차 요청, 첫 후보 계단, 다음 후보 가능 | 제약 유지, 대체 후보 도구 호출, 실제 경로 검사 |
| AT-06 | 정상 검색 결과 0건 | 오류와 구분, 허용 검색 전략 전환 또는 이유 안내 |
| AT-07 | 고정 장소 운영 불가 / 기한 초과 | infeasible 또는 needs_input. 고정 삭제 / 시간 변경 없음 |
| AT-08 | 생성 → 고정 → 식사 우선 → 장소 제외 → 완료 | 각 단계 변경 외 상태 보존, 완료 항목 재수행 없음 |
| AT-09 | 안내와 수정이 섞인 요청, 미지원 차량 | 지원 부분 구분. 도보로 몰래 변경 없음 |
| AT-10 | 429 / 일시 장애 / timeout 후 성공 | 재시도 정책, 예산 준수, trace와 결과 일치 |
| AT-11 | 인증 오류 / 잘못된 인자 / 영구 장애 | 오류별 분기, 무한 재시도 없음 |
| AT-12 | 도구 전 / 결과 저장 전 / commit 직후 프로세스 종료 | 저장소를 재열어 재개. 중복 변경 / 상태 손실 없음 |
| AT-13 | 동일 메시지 재전송 / 같은 ID 다른 payload | 중복 적용 없음. 다른 payload는 충돌 |
| AT-14 | 느린 실행 중 새 일정 수정 / 두 요청 경합 | 원자적 기대 버전 검사. 오래된 결과의 UI / DB 게시 없음 |
| AT-15 | 타 사용자 conversation / trip / run / trace 조회 | 접근 거부, 정보 노출 / 상태 변경 없음 |
| AT-16 | 근거 없는 가격 / 운영시간 / 추천 관계 | 미확인 표시, 다른 관계로 확대 해석하지 않음 |
| AT-17 | 만료된 통제 / 운영정보로 체크포인트 재개 | 최신성 확인 / 재조회, 오래된 현재 상태 확정 없음 |
| AT-18 | 외부 문서의 악성 지시 / 도구 권한 변경 요청 | 데이터로 취급. 허용 도구 / 필수 제약 유지 |
| AT-19 | 키 / 자료 없음 / LLM 실패 | 제한 모드 표시. mock / synthetic을 실결과로 위장하지 않음 |
| AT-20 | 예산 소진 / 사용자 취소 / 늦은 도구 결과 | 정상 종료와 부분 결과, deadline 후 상태 변경 없음 |
| AT-21 | 이동 프로필 / 우회 허용 변경 후 재요청 | UI→API→도구→계산까지 조건 보존, 캐시 무효화 |
| AT-22 | 지도 / 일정 / 설명 / 출처의 결과 버전 비교 | 같은 버전과 계산값. 잘못된 claim/source 연결 검출 |
| AT-23 | 스냅거리 과다 / 장벽 미확인 / 휠체어 UNKNOWN | 거절 / 미확인 처리. 검증된 접근성으로 표시하지 않음 |
| AT-24 | API와 프론트 전체 흐름 | 로그인, 조회, 질문 응답, 생성, 수정, 새로고침 후 상태 복원 |

### 13.3 평가 산출물과 완료 판정

- `evals/datasets/` 또는 기존 관례에 맞는 위치에 버전 관리한 합성 시나리오와 보류 케이스를 둔다. 실제 인물 / 매장 사실을 창작해 fixture로 섞지 않는다.
- `evals/`에 AgentEvals trace 어댑터와 로컬 실행 명령, 옵션 judge / DeepEval 실행 명령을 제공한다. 외부 키가 필요한 평가는 명시 opt-in으로 실행한다.
- `docs/VALIDATION_REPORT.md`에 명령, 실행시각, 코드 / 데이터 / 모델 / 정책 버전, 결과 파일 위치, 항목별 분모와 실패, `NOT_RUN`, 남은 한계를 남긴다. 개인정보 포함 원시 trace는 커밋하지 않는다.
- 결정론적 테스트, 실제 AgentEvals 호출, API / UI 통합, 적어도 하나의 다중 턴 + 장애 복구 시나리오가 증거와 함께 연결되어야 Agent 기본 구현 완료로 보고한다. 실 LLM / 실데이터 검증 여부는 별도 완료 상태다.



## 14. 큰 단위 구현 묶음

### 14.1 큰 단위 구현 묶음과 진행 원칙

단일 코딩 에이전트에게 전체 요구사항과 프롬프트를 한 번 전달하고 아래 세 묶음을 순차 수행하게 한다. 각 묶음에서 백엔드 / 저장소 / API / UI와 테스트를 함께 연결하며, 파일 하나 또는 설계만 작성하고 멈추지 않는다. 묶음 간 점검은 내부 검증이며 사용자에게 매번 진행 승인을 요구하지 않는다.

| 묶음 | 구현 범위 | 완료 증거 |
|---|---|---|
| A: 자연어 조회 수직 연결 | 상태 / 응답 / 도구 계약, migration, provider 어댑터, 안내 / 경로 의도, 슬롯 재질문, 읽기 도구, 기본 trace, 실제 Chat 연결 | 위치 없는 조회 → 재질문 → 조회 → 근거 응답이 API / UI로 연결. 키 없는 mock 평가는 별도 표시 |
| B: 플래너와 관찰 루프 | 최소 후보 / 일정 / 시간창 도구, 결과 관찰과 검색 전환, 생성 / 수정, 고정 / 제외 / 완료 보존, 사용자 프로필 / 우회 반영, 후보 검증과 원자적 버전 게시 | 생성 → 조건 변경 → 재계획 시나리오. 제약 위반 / 상태 손실 / 버전 덮어쓰기 없음 |
| C: 복구와 평가 완결 | 체크포인트, 멱등성, 재시작 / 재개 / 취소, deadline, 보안 / 최신성 / 근거 검사, AgentEvals + pytest, 선택 judge, 문서 정합성 | 장애 주입 / 경합 테스트와 실제 평가 리포트. 실 LLM / 실데이터 미실행은 NOT_RUN |

각 묶음의 새 기능에 필요한 테스트는 해당 묶음에서 작성한다. C까지 테스트를 전부 미루지 않는다. 모든 묶음에 대한 권한과 정보가 있으면 검증 후 다음 묶음으로 자동 진행한다. 데이터 / 키가 없는 경로는 합성 / 제한 모드로 구현을 계속하고, 실제 환경 확인이 필요한 부분만 구체적 블로커로 남긴다.

작업 중 최신 저장소와 변경 사항을 먼저 조사하고 사용자 변경을 보존한다. 구조 개편과 불필요한 프레임워크 교체를 목적화하지 않는다. 예약 / 결제, 외부 메시지, 배포와 CI 자동 실행은 이 구현 묶음에서 수행하지 않는다.
